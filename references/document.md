# Filling the document (step 9)

Read this before filling [template.html](template.html). Order: header (title, one or two sentences, repo tags, layer pills), the two summary cards, the three question cards, 「시나리오별 전후」 (step 4b, [scenario-rail.md](scenario-rail.md)), the impact path, the layer sections.

## Placeholders and fixed labels

Each `{{…}}` placeholder is an English instruction for what goes there. The comments are instructions too: delete them from the finished document, including the block of fixed strings above `<main>`. Replace every one with content in the output language, so none stays in the document. Fixed labels outside `{{…}}` are Korean output text: keep them in a Korean edition and swap them for the en strings in an English edition.

## Left summary card

Each fact is said once, where it belongs. The header lead says what the change is and why, not what breaks. The conclusion says what changes for whom. The warning block says who experiences what breakage. The 「직접 확인하는 법」 card says how to check and what to expect, and does not restate the conclusion or the warning. A scenario's head block holds only what is that scenario's own: a row that would only point back to the summary is deleted, not written. If the same sentence would appear in two of these, cut it from the lower one.

Contents: badge, conclusion (within 100 chars for ko, 160 for en), the warning when the badge is not `no`, the merge and rollout order table (`순서 | PR | 머리 커밋 | 먼저 끝낼 것` — order | PR | head commit | finish first) or the one-line 「배포」, and the rollback block. PRs and shas are written once in this table and not repeated in the header.

- **Rollout order table.** Each cell is one phrase, not a sentence. 「먼저 끝낼 것」 holds only order numbers or events (「없음」 "none", 「1 머지」 "merge 1", 「3 머지, 4 의 prod 배포」 "merge 3, prod deploy of 4"; with no PR or no prod stage, 「1 의 커밋」 "commit of 1", 「1 의 배포」 "deploy of 1", 「2 의 재시작」 "restart of 2"). A step the breakage depends on (a server restart that runs the migration, a tab reload) is a row of its own, not a note. No explanations like 「즉시」 ("immediately"), 「~전에」 ("before ~"), 「~를 확인한다」 ("check ~"); why that order is the job of the single warning block.
- **Rows that are not a PR** (web deploy, codegen regeneration, raising the minimum version) are allowed when the breakage depends on them: the PR cell names the action and the commit cell is 「없음」.
- **No PR at all** (a branch or an uncommitted working tree): one row per unit that ships, the PR cell naming it (「작업 트리 커밋」, 「<branch> 머지」), the commit cell the head sha or 「커밋 전」. The header says 「PR 0건」 and the issue key is left out of the title and lead. In the user impact table the first header becomes 「사용자 행동」, the last header names the shipping unit (「작업 트리 커밋」), and its cells are 「포함」 or 「범위 밖」.
- **Commit cell** holds the head commit only. The base commit is in the base table, so no "base → head" arrow. If PRs in the same step have different prerequisites, align to the later one and write a single step number.
- **Repo names** only on PRs not in the default repo. With PRs in two or more repos, the first sentence of the `.note` under the table is 「리포를 적지 않은 PR 은 <기본 리포> 다」 ("PRs without a repo are in <default repo>"); with one repo or no PR, leave that sentence out. Operational notes such as stacked-PR merge cautions go in the same `.note`, up to four sentences.
- **Shipping line or table.** Count the steps first: each PR, plus each step the breakage depends on (a server restart that runs a migration, a tab reload). One step gets the one-line `.ship` (「배포」: what is done, with the head commit in `<code>` or 「커밋 전」 since no table carries it, what runs at that moment, whether anything is released at all) and no table. Two or more steps get the table, and the note under it says whether a released version exists. Never both.
- **Conclusion** (`.verdict`): in the words a user or planner would use. No field names, status codes, or file names; those belong to the scenarios. `text_lint.py` reports `verdict-code` when it contains an identifier.
- **Rollback** (`.warn.back`, right under the warning): whether the previous version can run again after this ships. The label is 「되돌리기 가능」, 「되돌리기 불가」, or 「되돌리기 확인하지 못함」; the body says in plain words what going back means and what the way back is, then the evidence. It is drawn like a warning because an irreversible release is the heaviest fact on the page. A forward-only migration (a table rebuilt, a column dropped, data converted with no down migration) makes it 「불가」 unless you showed the old version opening the migrated data (SKILL.md step 6).
- **Warning block** (`.warn`, for every badge except `no`, placed directly under the summary conclusion): one breakage, at most two sentences. Its label is 「배포 순서」 for `yes` and `ord`, 「새로고침 전까지」 for `upd`. State only who experiences what, and for `ord` which side shipping first causes it, for `upd` until when. The preventing order is the rollout order table's job. Do not repeat the warning in the compatibility section; put only the remaining partial rollout states there as `.note`.
- **Existing-data warning** (a second `.warn`, labelled 「기존 데이터」, with any badge including `no`): only when shipping loses or hides data users already have (SKILL.md step 6). One or two sentences: what data, at which moment, and whether it can be carried over. The conclusion then leaves the loss to this block, and the line on existing data under the user-change table points here instead of repeating it.
- If `text_lint.py` reports `cell` on a cell in a summary card table, these rules are violated.

Right summary card: 「사용자에게 달라지는 것」, a table of `사용자 행동 | 지금 | 바뀐 뒤` (user action | now | after). One row per thing a user does, six at most, in the user's words with no identifiers; 「없음」 in 지금 when the action is new. A change no user can see has no row. Under it, one line on what happens to existing data. Requests, responses, and logs are not listed here; the scenario rails carry them. The User impact layer section then holds only what this table leaves out (evidence per row, more than six actions), folded.

## Question cards

Right under the summary, three cards named by what a reader asks, not by who the reader is. Teams differ in who reads (a planner, a reviewer, QA, an operator, support, or the author alone), but the questions are the same. Always all three, in this order. Each shows at most three lines (the size line of 「먼저 볼 곳」 is not one of the three); the rest is folded inside the card. A card with nothing to say keeps one line, 「없음. <근거>」, so the reader knows it was looked at.

- **「정해야 할 것」 (to decide).** What this change decided on someone's behalf: default values and names, limits, what gets deleted along with what, how long things are kept, on-screen wording (including text in the wrong language or tone), behaviour in edge cases, a trade-off taken (duplicate over loss). Write each as the current choice followed by a question someone can answer: 「목록을 지우면 안의 할 일도 지워진다. 확인 창이 필요한가?」. Take them from constants, migration defaults, validation limits, and UI strings in the diff. The folded part (「나머지 n건과 근거」) holds the remaining items and then the `file:line` of every item, the visible three included. Nine at most, the ones someone outside the code can answer first; a choice only a developer would weigh (an internal ordering, a timestamp that does not move) is left out. Anything the change left unintended and visible (the 「의도 밖 변경」 section) is listed here first.
- **「먼저 볼 곳」 (where to read first).** The size of the change in one line: `git diff --shortstat <base>` for files, added and removed lines, and the count of new files; for an uncommitted tree the untracked files are not in that total, so add their line count (「새 파일 13개(+1,271줄)」). Then up to three files to open first with one clause on what is there, chosen in this order: the migration or schema, the API contract (DTOs, routes), then the remaining source file with the most added lines in `git diff --numstat` (its two numbers are added and removed, not a sum), skipping lock files, generated code, and tests. Folded: premises the code itself states (a comment saying it assumes one instance, a migration's own header), each quoting the code's own sentence in 「」 with its `file:line`; a line you cannot quote from the code is your own finding and does not belong in this card. Three premises at most. Then the test functions in one line (total before and after, the two or three files where most were added, and whether you ran them: 「실행 결과: 통과 n개」 or 「확인하지 못함」), not a table per file. Only what the diff and the code state. This card does not hunt risk; it tells a reader where the weight of the change is.
- **「직접 확인하는 법」 (how to check).** Check items first: what to do and what must happen, in words a person can follow without the code. When the badge is not 「호환」 the first item is the warned breakage; when rollback is not possible one item checks that, and an existing-data warning gets one too; these stay among the visible three. Folded: how to get each version (branch, PR, or 「커밋 전 작업 트리」), the build and run commands (from the adapter note, or the ones you found), and the seed data the captures and checks start from. An item you could verify only through a test names the test instead of pretending a person can reproduce it.

These cards replace the old 「리뷰와 QA 가 확인할 것」 list. They do not repeat the conclusion, the warning, or the user-change table. A check item about the warned breakage is not a repeat: the warning says what the person experiences, the item says what to do and what must happen.

## Base and capture sources

Put them in a table. Do not chain "AS-IS is which commit, TO-BE is which commit, captures are from which run" into a paragraph.

- After the last scenario, one `.ft` table under the template's h3 「기준 커밋과 캡처 출처」 (`구분 | 리포 | 커밋 | 비고` — kind | repo | commit | notes).
- With two or more E2E runs, a run table (`회차 | 커밋 | 확인한 것 | 결과` — run | commit | what was checked | result). "What was checked" is one phrase per cell. As runs increase, add only rows. A run that mixes versions names each part in the commit cell (「화면 <sha>, 서버 <sha>」; for a rollback run, 「서버 <AS-IS sha>, 데이터 <TO-BE sha>」).
- `.note` only for one or two sentences of exceptions that cannot go in a table.
- How the document was made belongs in this table's 비고 cell and nowhere else: which tool found the boxes, that boxes were placed by hand, checksums, viewport and locale. The reader of a scenario does not need it.
- If `text_lint.py` reports `dense`, this rule is violated.

## Sections

- Each section has a `.lead` directly under the h2 with that section's conclusion in one line (skimming the TOC and conclusions reads the document). The template script handles the TOC, table wrapping, and layer pill links.
- Layer sections do not repeat what scenario panels showed; they hold exhaustive tables and full text (long payloads, all fields, all call sites). The `.lead` is what a skimming reader takes away, so a table of more than four rows is folded (`<details>` with the row count in its summary). The compatibility table stays open when the badge is not `no`. Folded blocks open by themselves when the page is printed.
- Delete sections for unchanged layers and move them as one line into 「변경 없는 레이어」 ("unchanged layers"). If every layer changed and no other line belongs there, delete that section too.
- Code and payload before/after (「모델 코드 전후」, 「payload 전문」, and the request cell of a scenario) are always the output of `scripts/code_diff.py`, one diff per model or payload, never hand-written rows or a hand-marked `<pre>` pair. It opens side by side and the reader can switch to unified; on a narrow screen, and in the scenario panels (`--view unified`), it opens unified. Line memos come from `--note`.
- The document is one file: every screenshot is inside the HTML (`scripts/inline_images.py`, SKILL.md step 9). Nothing in it points at a file on disk.
- The Data section is the entity diagram, then two folded blocks (「모델 코드 전후」, 「필드 전체 표」). The `.lead` and the diagram carry the conclusion; a block is left open only when it is the sole evidence for a side (no diagram for AS-IS, or a single field change with no diagram).
- Screen captures live in the scenario stages. Create a Screen layer section only when there are screens outside the stages, or to hold the evidence (`file:line`) for the step 3 「변경 없음」 judgment and the 「실물 없음」 lines. The 「mock 과 실물 차이」 line goes in that screen stage's `.note` and in the API spec section.
- A layer pill is `on` for any changed layer, whether or not it has a section. It becomes a link only when an h2 with the same name exists. Screen is covered by the scenario stages and User impact by the summary and impact path, so they need no section.
- The compatibility section's `.lead` counts rows, it does not retell: 「깨지는 호출처 1곳, 그대로인 호출처 4곳」. One consumer whose requests end differently (an open page whose add fails while its edit works) gets one row per outcome, and each row counts. What the broken call site experiences is in the summary's warning; the row gives the request, the status, and the evidence.
- A breakage is written out in full (status code, error text) in two places only: the row that is its evidence (the compatibility row) and the line memo on the field that causes it. The impact path, the field table, and the behaviour table name the field and its new rule (「필수」) and leave the status to those two.
- The compatibility section is mandatory when the badge is not `no`. If `no` and there are no call site rows, drop the section and put one line in 「변경 없는 레이어」: 「호환성: 바뀐 API 가 없어 깨질 호출처가 없다. <근거>」 ("compatibility: no API changed, so no call site can break. <evidence>").
- Separate `.where` in the impact path with commas (「web-app, features/settings」). Wrap paths and `file:line` in `.ev` with `<code>`.
- Order layer sections by impact on the reader, largest first (usually API spec, data, behavior, user impact, compatibility). Self-contained, no external CDN.
- The template's titles and separators already follow the writing rules; editing follows step 8.

## Markdown edition for the PR body (on request)

Summary, side-by-side table, impact path, merge and rollout order. Markdown cannot overlay boxes, so use PNGs with the boxes drawn in (`render.pair<N>.png` from step 7 as-is). Local image paths do not show in PRs, so use the project's image branch URL ([adapters.md](adapters.md)). If you cannot upload, write a placeholder and the local path.
