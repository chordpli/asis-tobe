# Screens: capture (step 4) and boxes (step 7)

Read this before capturing screens in step 4 and before marking them in step 7. The capture command, install command, and `NODE_PATH` per project are in [adapters.md](adapters.md).

## Capture (step 4, Screen)

Capture the same screen scenario on both sides. Keep data, language (one), and size the same.

Capture what the reader needs to see, not the whole viewport. When the content ends well above the bottom of the window, clip both captures to the same height, 24px below the taller side's content (a headless browser takes a `clip` rectangle); a capture that is half empty window doubles the length of the stage for nothing. When the page keeps its content in a centred column with empty margins, clip the width to that column as well (the same rectangle on both sides, wide enough for the wider version, and not narrower than 860px, the width a wide stage shows a capture at; a narrower image would be enlarged), so the text is not shrunk to fit margins nobody reads. Box coordinates are then relative to the clipped image. The reader can open any capture at full size by clicking it.

When the badge is not 「호환」, capture the broken state too: the screen the affected person sees (an old page showing the error after the new server is up), as a stage of its own in the scenario where it happens. Make it a pair of the same old page: left, before the deploy, doing the action successfully; right, after the new server is up, failing. Both sides are the old page, so the stage title and its `.note` say that the two sides differ by the server behind them, not by the page. The failing side may be taller (an error line appears): take the left capture, switch the server, take the right, then clip both to the taller one. A warning with no picture of what it looks like leaves QA and planners guessing.

1. Create one temporary worktree and install dependencies with the adapter's command. Installing and capturing take a long time, so run them in the background.
2. In that worktree, `git checkout <base>` and capture AS-IS.
3. In the same worktree, `git checkout <branch>` and capture TO-BE. If the PR changes dependencies, reinstall after the checkout.
4. If the scenario to capture exists only on the branch, in step 2 lay just the scenario definition files on top of the base commit. Find them with `git diff <base>...HEAD -- <scenario directory>`.
5. Compare the md5 of the two images and point out the changed spot in one line of text.
6. When done, `git worktree remove --force <temp>`. Never commit the temporary worktree.

- **Uncommitted TO-BE, or a repo you must not touch.** Do not check out, stash, or add a worktree. Export AS-IS with `git archive <base> | tar -x -C <temp>/asis` and copy the working tree to `<temp>/tobe` (leave out build output, `.git`, local databases). Build and run both there, with data files inside `<temp>` and a separate build output folder per version (a shared one lets the build tool reuse the first version's binary for the second). Before starting the servers, confirm the two binaries differ (checksum) and that each is the version you name.
- **No mock capture tool** (the server renders or serves the page): start each version's real server on its own port with its own empty data store, bring both to the same state through the API (the same items; when the request shape changed, each version gets the request it accepts), and capture with a headless browser at one fixed viewport, locale, and timezone. Write 「실제 서버(mock 아님)」 in the capture note (`.capnote`); that note holds this one phrase and nothing else. Take a copy of each data store right after seeding; step 10 re-measures against a copy, not the store the captures wrote to. A version that keeps its data in memory has no store to copy: a fresh process seeded the same way stands in for the copy. In your own capture script load `puppeteer-core` the way `render_check.mjs` does (`createRequire(process.env.NODE_PATH + '/')('puppeteer-core')`) or write the script as `.cjs`; an ES-module `import` does not look in `NODE_PATH`. Between runs, stop a server by the PID listening on its port and confirm the port is free before starting the next; a leftover process keeps answering from the old data store. To show what happens to existing rows, open a copy of the AS-IS data store with the TO-BE binary and read the rows after its migration runs.
- **Boxes from the browser, not from pixels.** When the layout moved (a sidebar appeared, a column widened) the pixel diff boxes most of the screen. In the same headless-browser script that takes the capture, read the changed elements' rectangles and turn them into % of the viewport: `const r = el.getBoundingClientRect(); ({x: r.left / W * 100, y: r.top / H * 100, w: r.width / W * 100, h: r.height / H * 100})`, where `W` and `H` are the width and height of the saved capture (the clip rectangle, not the window: a clipped capture is shorter than `innerHeight`). Use those as the box coordinates and skip `diff_boxes.py` for that pair.

- **When AS-IS has no entry point** (a new screen behind a new button): write a separate temporary comparison scenario that stops at the preceding state common to both sides, and capture that state on both sides. Capture the new screen itself only in TO-BE, and leave the AS-IS cell as 「실물 없음: <진입점이 없는 근거>」 ("no real artifact: <evidence there is no entry point>"). The same scenario failing in AS-IS while waiting for the entry point is that evidence. When two new scenarios start from the same preceding state, the pair of that state goes in the first one only; the second holds its TO-BE capture and one line pointing back.
- **A capture shows a change that belongs to another scenario** (a new button of scenario 2 visible on scenario 1's TO-BE screen): do not box it; one line in the stage's `.note` names the scenario that covers it.
- **Check mock responses against the API spec** (only when the capture used mocks). If a screen scenario's mock differs in shape from the real payload (fixture, OpenAPI), write one line in the screen section: 「mock 과 실물 차이: <무엇>」 ("mock vs. real difference: <what>"). If the screen holds only for the mock's shape, that fact is a review point.
- **Lightweight fallback.** Only if the platform cannot be captured (e.g. native) or step 3 of SKILL.md found the changed branch unreachable with current data, do not fake it: put 「실물 없음: <이유>」 in the screen panel and show the old and new appearance through the test assertion strings and `file:line` of the rendering code.

## Stage layout (step 7)

For each screenshot pair, draw boxes over the changed spots on the image. Never leave just the picture and say "find what changed."

Screen pairs go in the screen stage (`.stage`) at the end of the scenario. Phone captures keep the device frame; wide captures such as web or admin use `.stage.wide` (no frame, numbered descriptions below). In a wide stage the two captures stack, AS-IS above TO-BE, so each stays readable; the swipe and onion-skin modes overlay them. If there are more screens outside the scenarios, add another stage in the Screen layer section.

## Boxes (step 7)

0. **No capture on either side** (platforms that cannot be captured, such as native): drop the stage and put `<p class="missing">실물 없음: <이유></p>` inside the screen panel.
   **Only one side has an image** (AS-IS 「실물 없음」): do not run the script. Use `.stage.solo` and delete `.tools`, `.frame.a`, `.slide`, `.cut`. Under the stage head put `<p class="missing">실물 없음(AS-IS): <이유 한 문장></p>` ("no real artifact (AS-IS): <reason in one sentence>") and fold the remaining evidence. Place boxes by hand by measuring the new element's position on the image that exists. A wide capture with one side is `class="stage wide solo"`.
1. **Extract coordinates**: `python3 -I <skill>/scripts/diff_boxes.py <ASIS.png> <TOBE.png>`. (`<skill>` is this skill's base directory, as in SKILL.md.) Both must be the same screen scenario at the same viewport width. The script does not count parts that only shifted vertically (e.g. one card inserted in the middle pushes everything below down as a block; only the inserted card is boxed). `asis` and `tobe` in the output are % coordinates relative to each image. If `same: true`, no boxes; 「변경 없음」.
2. **Choose boxes.** Pixel differences are not semantic units. Split a box where distinct changes merged; merge boxes where one change was fragmented. Discard boxes unrelated to the change: clocks, animations, a fixed bottom button cut off at a scroll boundary.
   - If the page width or a column width changed, elements that only moved sideways also come out as boxes; discard them and say so in one line of `.note`.
   - `shifted: true`: do not use the script's boxes; measure the changed element's position in the screenshot and write it as %.
   - `anchored: true`: an element attached to the bottom of the screen (chat input, bottom sheet) changed. The box's top/bottom edges may cut through a text line; open the screenshot and adjust to line boundaries.
3. **Place marks.** Inside the template's `.shot`, one `.mark` per box. AS-IS boxes (`.frame.a`, dashed with hatching) mark the spot before it vanished or changed; TO-BE boxes (`.frame.b`, solid) mark the spot after it appeared or changed. Numbers are `<span class="n a">1</span>` (square) and `<span class="n b">1</span>` (circle). The same change gets the same number on both sides. A one-side change (addition or removal) is marked only on that side. Set the original `width` and `height` on the `img` so the layout does not jump. `src` is the capture's file path while you work; `inline_images.py` puts the image inside the HTML at the end (SKILL.md step 9).
   - **Number covers the text.** The number sits inside the box's top-right corner. On a small target (a button, a counter, a status label) it covers the text: add `out` to hang it below the box (`<span class="n b out">2</span>`), `out up` above, plus `l` to align left. Do not write inline styles for this, and do not leave a covered label. A number is about 22px on screen whatever the image size; a wide stage shows a 1280px capture at about two thirds, so on the image it takes about 34px. Leave that much clear next to the box. `out up` on an element at the very top of the capture pushes the number outside the image; use `out` (below) there. Two changes on adjacent lines that numbers cannot label apart share one box and one callout that names both.
   - The stage-head buttons switch between side by side, swipe, and onion skin. Swipe by dragging the image or the bar below; onion skin changes TO-BE opacity with the bar. 「바뀐 곳 표시」 ("show changes") toggles the boxes. The two images must be the same size. Without JavaScript, or when printed, it stays side by side.
   - If the two captures' scroll positions differ and misalign when overlaid, put one line of reason in `.capnote.offs` (visible only in swipe and onion skin). Otherwise delete it.
   - **Two or more captures in one scenario** (e.g. right after a failure, then after the user fixes it): one stage per capture, in the order the user sees them, with ids `s<N>-stage`, `s<N>-stage-2`. Each stage gets its own one-line title and its own callouts; box numbers restart at 1 per stage. Do not merge two moments into one image pair.
4. **Callouts.** To the right of the stage (below, for web), in `.callouts`, one card per number holding both sides of that change: the AS-IS line and the TO-BE line together (`.sides`), or one line alone when only one side has it (`.sides.one`). Never one card per side; the reader should not meet the same number twice. Wrap on-screen text in quotation marks (「」 in the Korean edition, “ ” in the English edition). What a reader of the screens must know (a substitute capture, a mock that differs from the real payload) goes below in `.note`. How you made the capture or found the boxes does not; that goes in the base table's 비고 cell ([document.md](document.md)).
5. **Render check.** See the gate in SKILL.md step 7. Outputs: `render.<scheme>.<width>.<NN>.png` (the whole page with all `<details>` and all six scenario cells expanded, cut top to bottom into slices 2,000px tall, for both schemes and 420px width), `render.first.<width>.png` (the first screen as the reader meets it, nothing opened, at the given width and at 420px), and `render.pair<N>.png` per stage. Read text from the slices; the JSON line's `slices` says how many each variant has. Run it even for documents without screen pairs; the purpose is layout checking. Open `render.pair<N>.png` directly to check whether boxes cover text and where numbers sit. Wherever the coordinates came from, if a box border touches text, widen it. Not covering text wins.
